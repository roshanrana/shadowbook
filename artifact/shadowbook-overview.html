The problem

Core migrations fail in the last two percent

Not on the happy path. They fail in the residue of reconciliation breaks, and those are almost always undocumented behaviour in the incumbent — a rounding rule, a cut-off boundary, a fee waiver nobody wrote down, a holiday the old system does not observe.

You cannot test against behaviour nobody has written down. You can only run both systems side by side and watch where they disagree. So: a shadow ledger, a legacy simulator carrying twelve deliberate divergences, a reconciler working at three grains — and an honest measurement of how long each divergence took to surface.

Reconciliation is a tripwire, not a diagnosis

Every seeded behaviour surfaced, most within the first working week — but only three produced a break signature naming exactly one cause. That is structural rather than a tuning gap: signatures are integer predicates over a delta, and distinct behaviours produce the same delta shape. More rules cannot fix it, because the information needed is not in the delta.

Cadence sizes the window; the calendar places it

A month-end quirk cannot be found before month end, however sensitive the reconciler is. Two month_end quirks behave identically and were found on day 2 and day 25 — because W1 opens on 2028-02-28, so a leap-day month end falls on business day 2 and the next not until day 25. A four-week pilot that happens to sit between two month ends exercises none of that behaviour and reports clean.

Finding 2

What each delivery design actually costs when the broker dies mid-payday

Three Redpanda brokers at replication factor 3, killed and restarted on a quorum-preserving schedule. 36,000 movements per run, three runs per configuration, median with min–max in brackets.

Consumer configuration Applied Lost Duplicated Zero-sum invariant
A — at-most-once 36000 [35975–36000] 0 [0–25] 0 [0–8472] held
B — at-least-once 36000 0 4959 [0–8950] held
C — at-least-once + inbox 36000 0 0 held

A did both, and that is the row worth reading twice

At-most-once is the only configuration here that lost anything — 25 movements produced, acknowledged by the cluster, never applied. It also duplicated, because its guarantee holds only while the offset commit survives, and a coordinator failover can lose the commit. It buys “no duplicates” while commits are durable and pays with real loss when they are not: the worst of both outcomes, arrived at honestly.

C duplicated nothing, because suppression is a constraint

A redelivered message collides on inbox_pkey and the whole transaction rolls back. That is a database constraint rather than a race that usually goes the right way — which is why the zero appears in every run rather than most of them.

The invariant held in all nine runs — and that is the point

A duplicated posting is perfectly balanced and completely wrong. Correctness at the row level does not imply correctness at the ledger level, and no internal invariant can close that gap. It is precisely why a second source of truth exists.

Counts for A and B are net, not exact

Neither keeps an inbox, and both mint a fresh posting id per delivery, so nothing records which movement an effect came from: a run that lost 100 and applied 100 others twice is indistinguishable from a clean one. Latency is empty for the same reason. That is not a limitation of the harness — without an inbox the system is not measurable from its own data.

What building it found

Nine defects, and only one of them failed loudly

Five sat in a chaos profile that had been written, reviewed and committed six weeks earlier — and never once started. Four more were in the measurement harness itself.

Chaos profile

Kills that matched nothing

Chaos killed brokers by name; Compose generates <project>-redpanda-1-1. A failed kill is recorded, not fatal — so the sweep would have completed cleanly having killed nothing.

Chaos profile

A property that does not exist

unclean_leader_election_enabled is a Kafka name with no Redpanda equivalent. Inert since the day it was written, while the config header advertised the guarantee on its strength.

Chaos profile

Cluster settings applied as node settings

Four properties silently ignored, so the profile claimed RF=3, minimum replication and transactions it did not have. Only one of the five failed loudly; the rest would have produced entirely reasonable numbers.

Harness

122,886 losses that never happened

The drain detector capped total wait rather than stalls, so everything the consumer had not yet reached was recorded as permanent loss — records sitting on the broker, intact. Every fixed parameter agreed, so every guard would have rendered that table.

Harness

44,746 applied against 36,000 sent

Runs were isolated; sweeps were not. Run ids repeat between sweeps, so the second attached to the first sweep’s topics and consumed an experiment already discarded. C exposed it; A and B concealed it as duplication, where it looked like a finding.

Harness

Duplication that was structurally zero

Mode B applied 26,221 effects for 12,000 movements and reported zero duplicates, because duplicated = postings − applied is identically zero without an inbox.

The failures worth guarding against are the ones that produce a plausible number. An exception is easy to notice. A confidently wrong table is what reaches a decision-maker.

So each one became a refusal, not a comment

Seven guards now decline to render a finding rather than render a doubtful one: a table built from an in-process broker, one mixing simulated with real runs, one containing a run cut off mid-drain, one where applied exceeds sent, one folding two sweeps together, one whose rows differ in seed, rate, schedule, SHA or broker version, and one presenting net counts as exact.

Limits

What this does not prove

The quirks are seeded and known. This calibrates a twin’s reconciliation; it does not discover unknown behaviour.

A simulator is not a core. A real incumbent has decades of divergences, and they interact in ways this cannot reproduce.

Single-box numbers are not production numbers. The throughput target in the requirements was not met on the available hardware, and the ship report says so.

Finding 2 ran at 200 movements/s, not the specified 1,000/s, because the consumer sustains ~280/s on that host. Valid as a comparison between configurations under identical chaos; not the specified rate.

Configuration D is implemented and has never run. The in-process fake cannot verify transactional producer ids, so only a real cluster can.

Quirks compound. Twelve are detected in isolation, eleven with all twelve enabled at once — because some change which transactions land on which business day and destroy the ratios others would show. Both numbers are in the report.

Portfolio work built to production constraints. No real money, no real data, not a production system. The ship report is the honest account of what is and is not measured.
